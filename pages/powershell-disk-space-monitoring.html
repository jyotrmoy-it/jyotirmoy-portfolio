Start automating with disk space monitoring.

A practical first PowerShell health check: inspect fixed disks, identify low free space, report across servers and build a repeatable routine.

🚀 Want to start your PowerShell automation journey? Don't begin with a complicated script. Start with disk space monitoring.

Imagine looking after 20, 50 or even 100 Windows servers. How would you know a volume is running low on free space before users start noticing a problem?

You can build your first useful health check with a few lines of PowerShell. It is a simple, read-only starting point—not a replacement for an enterprise monitoring platform.

Your first PowerShell disk-space report

Run this locally in a PowerShell session to list fixed disks and show free and total capacity in GB:

Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
Select-Object DeviceID,
@{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB,1)}},
@{n='SizeGB';e={[math]::Round($_.Size/1GB,1)}}

What does it do?

  • Get-CimInstance reads disk information from the Windows logical disk class.
  • DriveType=3 selects local fixed disks, excluding network and removable drives.
  • FreeSpace and Size are converted from bytes to GB and rounded to one decimal place.
  • Select-Object shapes the output into a compact report.

Take it one step further: add free-space percentage

A percentage makes it easier to compare volumes of different sizes and establish a threshold for investigation.

Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
Select-Object DeviceID,
@{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB,1)}},
@{n='SizeGB';e={[math]::Round($_.Size/1GB,1)}},
@{n='FreePercent';e={
    if ($_.Size -gt 0) {
        [math]::Round(($_.FreeSpace / $_.Size) * 100,1)
    } else { 0 }
}}

For example, your team might choose to review a volume when free space falls below an agreed threshold such as 15%. The right threshold depends on workload, growth rate, capacity and operational policy—there is no universal number.

Monitor multiple Windows servers

Once the local report works, you can run the same read-only query remotely with Invoke-Command. Start with a small, approved test list:

$Servers = @('JM-TEST-GHOST')

$DiskReport = Invoke-Command -ComputerName $Servers -ScriptBlock {
    Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
    Select-Object @{n='Server';e={$env:COMPUTERNAME}},
        DeviceID,
        @{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB,1)}},
        @{n='SizeGB';e={[math]::Round($_.Size/1GB,1)}},
        @{n='FreePercent';e={
            if ($_.Size -gt 0) {
                [math]::Round(($_.FreeSpace / $_.Size) * 100,1)
            } else { 0 }
        }}
}

$DiskReport | Format-Table -AutoSize
Before running remotely:

PowerShell remoting/WinRM must be configured and reachable, and your account needs the appropriate permissions on the target servers. Follow your organisation's approved access process. Test connectivity and error handling first; do not enable remoting broadly just to run an example.

Export the results to CSV

A CSV makes it easy to review results, filter low-capacity volumes and share a report with the authorised operations team.

$ReportPath = ".\DiskSpaceReport.csv"
$DiskReport |
Export-Csv -Path $ReportPath -NoTypeInformation -Encoding UTF8

Write-Host "Disk report saved to $ReportPath"

For recurring reports, use a controlled output location with appropriate access permissions, retention and storage capacity. Avoid placing operational reports in a public folder.

Schedule a daily health check

  1. Validate the script manually against a small test group.
  2. Add logging, timestamps, error handling and a clear exit/status result.
  3. Run it under an approved service identity or managed execution identity with least privilege; never embed a password in the script.
  4. Create a Windows Task Scheduler task using your organisation's standard deployment and change-control process.
  5. Review the output and failures regularly. A scheduled task that silently stops running is not reliable monitoring.

Three golden rules for trustworthy automation

  • Read-only first. Collect and validate information before considering any action that changes a system.
  • Log every execution. Record when it ran, which targets were checked, what succeeded and what failed—without logging secrets.
  • Never hardcode credentials. Use approved credential-management or managed identity approaches and grant only the permissions required.

The best automation engineers do more than write scripts. They build dependable workflows that save time, reduce repetitive manual work and help teams identify risks before they become incidents.
