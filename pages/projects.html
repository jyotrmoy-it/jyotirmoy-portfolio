01Investigating high CPU or memory usageServer performance troubleshooting

Problem

A production server becomes slow, applications respond late, or monitoring reports sustained CPU or memory pressure.

Investigation and resolution workflow

  1. Confirm scope, start time, affected services and business impact. Compare current CPU, committed memory, paging, disk latency and network counters with a known-good baseline.
  2. Use Task Manager, Resource Monitor, Performance Monitor and PowerShell (Get-Process, Get-Counter) to identify the processes and resource trends involved.
  3. Correlate process activity with Windows System/Application logs, scheduled tasks, recent deployments, antivirus scans and application events. Check whether the bottleneck is CPU, memory, storage or an external dependency.
  4. Test a targeted, reversible fix in a controlled window: correct a runaway process or application defect, adjust an approved workload schedule, or engage the owning team. Avoid terminating critical processes without impact assessment.
  5. Monitor the same counters after the change and document the before/after evidence.

Validation and evidence

Compare peak and sustained CPU, available/committed memory, paging, disk latency, application response time and incident recurrence across equivalent workload windows. Record the actual baseline and post-change values; do not claim improvement without telemetry.

02Recovering a failed Windows serviceService outage diagnosis and prevention

Problem

A Windows service stops unexpectedly or fails to start, interrupting an application or dependent business process.

Investigation and restoration

  1. Confirm service name, startup type, current state, dependencies, recovery options and the exact error/time from Services, Get-Service and Event Viewer.
  2. Review Service Control Manager events, application logs, recent patches/configuration changes, service account status, permissions, certificates, ports and required files.
  3. Check dependencies and resource availability. Validate credentials and least-privilege rights; never place passwords in scripts or logs.
  4. Restore using the approved runbook: correct the root cause, start the service, confirm dependent services and perform a functional application test. Use a rollback plan if the change worsens impact.
  5. Prevent recurrence with alerting, dependency documentation, service-account governance, change validation and a tested recovery procedure.

Validation

Confirm service state remains Running, event logs are clean, health checks succeed and the dependent application works. Track repeat failures and mean time to restore.

03Improving Windows Server patch managementControlled updates and maintenance windows

Problem

Servers miss security updates, patch cycles are delayed, or unplanned restarts create avoidable disruption.

Process improvement

  1. Inventory servers by role, owner, criticality, OS version, maintenance window and reboot tolerance.
  2. Define a patch policy: assess advisories, test updates on representative non-production systems, approve deployments, communicate impact and define rollback/restore criteria.
  3. Use an appropriate management platform such as Windows Server Update Services (where supported), Microsoft Configuration Manager or an approved cloud management service. Group servers into pilot, standard and critical rings.
  4. Schedule deployments in approved maintenance windows. Confirm backup/restore readiness, application-owner availability and reboot coordination before rollout.
  5. Monitor installation status, failed updates, pending reboots and compliance; investigate exceptions and report them to owners.

Measures

Track patch compliance by deadline, missing critical updates, deployment lead time, failed installation rate, reboot-related incidents and exception age. Compare equivalent reporting periods; publish real figures only after validating the source reports.

04Resolving Active Directory authentication problemsSign-in failures and identity troubleshooting

Problem

A user or service experiences a verified domain sign-in failure, repeated lockout or inconsistent authentication across systems.

Investigation and recovery

  1. Capture the exact error, timestamp, user/device context and affected scope. Check whether the issue affects one account, one endpoint, one site or many users.
  2. Review relevant Domain Controller security/system events and authentication diagnostics. Check account status, lockout, expiry, logon restrictions and recent password changes.
  3. Validate DNS, domain-controller discovery, time synchronisation, network reachability, replication health and secure channel where applicable.
  4. Check stale stored credentials, mapped drives, scheduled tasks, services and applications that may repeatedly submit an old password.
  5. Restore access using approved identity procedures, then confirm successful sign-in and monitor for repeated lockouts. Escalate suspected compromise through the security process.

Prevention

Document common error codes, account lockout triage, DC/DNS checks, replication monitoring and escalation paths. Never expose usernames, domain names or internal event data publicly.

05Controlling Windows Update and automatic restarts with GPOWhy it matters · how to configure · how to keep servers updated

Why this is needed

Uncoordinated updates or restarts can interrupt critical workloads. A policy-based approach gives administrators predictable maintenance windows, staged deployment and visibility. The objective is controlled patching, not permanently disabling security updates.

How to implement (domain-managed servers)

  1. Design server groups by role and criticality. Define maintenance windows, application-owner approval, backup checks, reboot coordination and an emergency patch path.
  2. In Group Policy Management, create and link a dedicated GPO to a test OU first. Use security filtering so only the intended server group receives it.
  3. Navigate to Computer Configuration → Policies → Administrative Templates → Windows Components → Windows Update (the exact subfolder names can vary by Server version/ADMX templates).
  4. Configure Configure Automatic Updates according to the update-management design. With WSUS, point clients to the approved intranet update service and use staged approvals. Microsoft documents option 4 for scheduled installation; Server 2016 and later also document option 7 for download and administrator-controlled installation/restart.
  5. Review restart-related policies carefully, including No auto-restart with logged-on users for scheduled automatic updates installations and scheduled restart behaviour. These settings have scope/interaction limitations and are not a substitute for a maintenance and patch-compliance process.
  6. On a pilot server run gpupdate /force, verify resultant policy with gpresult /h C:\\Temp\\gpo-report.html, confirm WSUS/management-agent reporting, install an approved test update and validate reboot behaviour.
  7. Roll out in rings after approval. Monitor update compliance, failed installations, pending reboots and exceptions; keep a documented rollback/recovery plan.

How to update these servers safely

Synchronise and review updates, approve them for a pilot group, deploy during the agreed window, check application health, reboot only as planned, validate services and event logs, then promote the same update set to the next ring. Record exceptions and remediate missed patches. For cloud VMs, use the organisation's supported update-management service and maintenance controls rather than assuming an on-premises WSUS design applies.

Important: Do not broadly block Windows Update or disable automatic updates as a permanent security measure. GPO settings differ by Windows Server release and ADMX version. Test in a lab/OU, check resultant policy and consult the server-specific Microsoft guidance before production rollout.

Official guidance: Configure WSUS client Group Policy · Configure WSUS.

06Deploying Multi-Factor Authentication (MFA)Why MFA matters and enabling it in a cloud environment

Why MFA is needed

A password alone can be phished, reused or stolen. MFA requires another proof of identity and reduces the chance that a compromised password alone grants access. Prioritise administrators, remote access, email, finance and other sensitive applications.

Microsoft Entra cloud implementation example

  1. Inventory users, privileged roles, cloud applications, legacy authentication, service accounts and emergency access accounts. Confirm licensing and identity architecture.
  2. Choose the control model: Security Defaults for a straightforward baseline where suitable, or Conditional Access for granular policies (licensing requirements apply). Avoid mixing incompatible approaches without planning.
  3. For Security Defaults, sign in to Microsoft Entra admin center with an appropriately privileged role; open Entra ID → Overview → Properties → Manage security defaults, set Enabled and Save.
  4. For Conditional Access, create a policy requiring MFA for selected users/groups and cloud apps; exclude only carefully governed emergency accounts, test with a pilot group, and use report-only mode where available before enforcement.
  5. Configure registration and user communication. Prefer phishing-resistant methods such as passkeys/FIDO2 or certificate-based authentication where supported; provide secure recovery and help-desk verification procedures.
  6. Validate sign-in logs, policy evaluation, registration coverage, failure scenarios and emergency access. Roll out in phases and monitor risky sign-ins.

Operational safeguards

Maintain at least two monitored emergency access accounts according to Microsoft's guidance, alert on their use, review exclusions and test recovery. Protect privileged roles with stronger controls and separate admin identities.

Official guidance: Mandatory MFA setup · Enable MFA with Conditional Access.

07Improving access provisioningRequest, approval and fulfilment controls

Problem

Informal requests can lead to delays, incomplete approvals or incorrect permissions.

Standard workflow

  1. Use one request channel with identity, manager, role, business justification, systems, access level and required date.
  2. Route approval to the manager and system/data owner; require security approval for privileged or sensitive access.
  3. Fulfil from approved role templates, verify the target identity and apply least privilege.
  4. Notify requester and approver, record the change/ticket ID and retain evidence in the approved system.
  5. Set expiry/review dates for temporary access and reconcile requests against actual entitlements.

Measure

Track median request-to-approval and request-to-fulfilment time, rework rate, rejected requests and access errors. Establish a baseline before reporting improvement.

08Introducing role-based access control (RBAC)Consistent role permissions and least privilege

Problem

Direct user-by-user permissions become inconsistent and difficult to review as teams and systems grow.

Implementation

  1. Inventory access groups, application roles, data sensitivity and current entitlements.
  2. Work with business owners to define job-based roles and a permission matrix. Separate standard, elevated and emergency access.
  3. Map roles to directory groups or cloud app roles; assign users to roles rather than granting ad-hoc permissions.
  4. Use separate privileged accounts, approval and time-bound elevation for administrative work where supported.
  5. Pilot, test access boundaries and negative cases, then migrate in phases with rollback and owner sign-off.

Measures

Review number of direct grants, orphaned permissions, role exceptions, access review findings and provisioning errors.

09Reviewing and removing outdated accessPeriodic access certification

Problem

People change roles, leave teams or stop using applications while old access remains active.

Review process

  1. Generate a scoped entitlement report from authoritative identity and application sources.
  2. Have managers and resource owners certify whether each access grant is still required.
  3. Flag inactive accounts, excessive privileges, duplicate access and accounts without a clear owner.
  4. Revoke approved access through controlled change tickets; preserve required audit evidence and validate removal.
  5. Escalate overdue reviews and track exceptions to closure.

Measures

Track review completion, overdue decisions, stale entitlements removed, exception age and access recertification coverage.

10Strengthening joiner, mover and leaver (JML) processesTimely access changes throughout the employee lifecycle

Problem

Manual handoffs can leave new starters waiting, role changers with excess access or departing employees with active accounts.

Documented lifecycle

  1. Joiner: receive an authoritative HR trigger, validate identity and start date, assign approved baseline role, equipment and application access.
  2. Mover: obtain new manager/resource-owner approval, grant new role access and remove old permissions based on an agreed transition plan.
  3. Leaver: use an authorised termination trigger, disable sign-in at the approved time, revoke sessions/tokens, recover assets, transfer data ownership and remove access keys/secrets.
  4. Record every action, owner, timestamp and exception in the ticket/workflow system.
  5. Reconcile HR records with directory/cloud accounts and review service/shared accounts separately.

Measures

Track time to provision, time to deprovision, missed lifecycle tasks, access exceptions and audit findings. Coordinate with HR, Legal and Security policies.

11Reducing incident resolution timeTriage, escalation and service restoration

Problem

Incidents wait in the wrong queue, arrive without diagnostic information or are escalated inconsistently, increasing time to restore service.

Workflow change

  1. Define impact/urgency priorities, severity criteria, ownership and escalation thresholds.
  2. Create a triage checklist: affected service/users, start time, scope, error, recent change, business impact and troubleshooting already performed.
  3. Route by service ownership and skill; set acknowledgement and update expectations.
  4. Introduce a major-incident bridge/runbook for high-impact events and capture decisions, timestamps and communications.
  5. Review aged tickets and recurring bottlenecks weekly; update routing rules and knowledge articles.

Documentation

Priority matrix, triage checklist, escalation matrix, major-incident runbook and closure template.

Measurable outcome

Measure mean/median time to resolve (MTTR), first-response time, reassignment count, SLA attainment and reopen rate. Compare similar incident types and report sample size and date range.

12Standardizing IT documentationShared knowledge base and runbooks

Problem

Knowledge is held in personal notes or chat threads, causing repeat questions, inconsistent fixes and slow onboarding.

Process and documentation

  1. Identify high-volume tasks and recurring incidents from ticket data.
  2. Create a common article template: purpose, symptoms, prerequisites, risk, step-by-step resolution, validation, rollback and escalation.
  3. Assign an owner, reviewer, version, last-reviewed date and audience to every runbook.
  4. Publish in an approved searchable knowledge platform with role-based access and change history.
  5. Review articles after incidents, platform changes and scheduled knowledge audits.

Implementation and measures

Pilot with one support queue, train agents, link relevant articles to tickets and gather feedback. Measure article usage, repeat-ticket rate, time to onboard, search success and time-to-resolution.

13Automating routine support tasksAccount setup, password workflows and software requests

Problem

Repetitive manual requests consume technician time and introduce inconsistent steps.

Safe automation approach

  1. Select a frequent, low-risk task with stable requirements and a clear owner.
  2. Map approvals, inputs, identity verification, pre-checks, execution, logging and exception handling.
  3. Build an idempotent, least-privilege workflow using approved tools (for example, PowerShell with controlled service identities or an ITSM automation platform).
  4. Keep secrets in an approved vault; validate inputs; log actions without exposing passwords or personal data.
  5. Test success, failure, duplicate requests, rollback and audit trails in a non-production environment.
  6. Deploy gradually with monitoring, owner review and a manual fallback.

Documentation and measures

Maintain workflow diagram, runbook, permissions matrix, test cases and support procedure. Measure manual minutes per request, turnaround time, failure/rework rate and automation adoption. Never claim hours saved without a defensible baseline.

14Reducing recurring IT issuesRoot-cause analysis and problem management

Problem

The same symptom returns because incidents are resolved individually without identifying the underlying cause.

Problem-management process

  1. Group related incidents by service, symptom, error signature and time pattern.
  2. Prioritise by frequency, impact, risk and business disruption.
  3. Build a timeline and use evidence-based analysis (change correlation, logs, monitoring, configuration and dependency review).
  4. Document root cause or clearly label an unresolved hypothesis; define workaround and permanent corrective action.
  5. Assign owners and due dates, test the fix, deploy through change control and monitor recurrence.
  6. Update known-error records, runbooks and monitoring thresholds.

Measures

Track repeat incidents per service, recurrence within 30/60/90 days, problem backlog age, corrective-action completion and service downtime.

15Creating a self-service knowledge portalFAQs and guided user support

Problem

Users raise tickets for common tasks because trusted instructions are hard to find or written only for technical staff.

Implementation

  1. Analyse ticket categories to identify safe, repeatable self-service candidates.
  2. Write plain-language FAQs with prerequisites, screenshots only from approved test environments, clear steps and a “when to contact support” route.
  3. Organise articles by user goal, add search tags and keep sensitive admin procedures behind restricted access.
  4. Ask a small user group to test findability and comprehension before launch.
  5. Promote the portal in service-desk replies, onboarding and internal communications; review feedback and article freshness.

Measures

Track article views, helpfulness, search-with-no-result rate, ticket deflection (using a defined method), repeat contacts and user satisfaction. Do not equate page views alone with tickets avoided.
